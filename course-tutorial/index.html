Module 01 · 项目概述

FilePress Blog — 文件即数据

一款"零数据库、零 CMS、纯 Markdown 文件驱动"的 VitePress 1.4 技术博客引擎。本模块带你了解它的设计哲学、技术选型与整体架构。

What is this

一个"用文件夹就能写博客"的系统

FilePress Blog 把 frontmatter 写在 Markdown 文件里，把文章放在 content/posts/ 下， VitePress 在构建期 扫描目录生成静态 HTML，浏览器里看不到任何数据库、任何 API 调用 —— 整个产物是一堆可直接托管到 CDN 的纯静态文件。

Core idea

Markdown 文件就是数据库本身。不需要后台、不需要管理员面板、不需要备份策略 —— git push 就是备份，git clone 就是迁移。

它解决了一个什么痛点？

传统博客系统（WordPress、Hugo 模板、Headless CMS）要么需要维护数据库，要么需要登录后台写作。FilePress Blog 把这两件事一起砍掉：

传统方案 · 你要做的事

登录 WordPress 后台 → 在 WYSIWYG 编辑器里写 → 担心插件冲突 → 备份 MySQL 数据库 → 配置 Nginx + PHP-FPM → 每月打安全补丁……

FilePress Blog · 你要做的事

用任意编辑器写 .md → git push → 完事。CI 自动构建、自动部署到 GitHub Pages，文章版本跟着 git 走。

Step 0 · 准备

先确认你的机器"够格"

FilePress Blog 对环境只有两条硬性要求：Node.js ≥ 20，pnpm ≥ 9。除此之外没有任何外部依赖（不装 MySQL、不装 Redis、不配 Nginx）。

01
Node.js ≥ 20

建议用 nvm 管理多版本；macOS / Linux 用户 nvm install 20 && nvm use 20，Windows 使用 nvm-windows。

02
pnpm ≥ 9

npm i -g pnpm。FilePress Blog 锁定了 esbuild / sharp / vue-demi 的 build 脚本，pnpm-workspace.yaml 已在仓库中配置。

03
Git

仅当你准备 git push 部署到 GitHub Pages 时需要，本地预览不强制安装。

ⓘ

Why pnpm, not npm?

pnpm 的硬链接机制能让 node_modules 在多项目间共享，安装速度比 npm 快 2-3 倍，磁盘占用也更小。FilePress Blog 的 CI 工作流也基于 pnpm 编写。

数据加载器：让"分类页 / 标签页"知道该生成哪些路径

VitePress 的 .paths.ts 机制是它能"构建期确定所有路由"的关键。posts/[slug].paths.ts、tags/[tag].paths.ts、categories/[category].paths.ts 三者配合，生成出 /posts/vue3-reactivity、/tags/前端 这类动态路由。

posts/[slug].paths.ts 

            import { scanPosts } from '@theme/utils/posts'
            
            export default {
              paths() {
                const posts = scanPosts()  // 扫描 content/posts/
                return posts.map(p => ({
                  params: { slug: p.slug },
                  content: p  // 整篇文章传入模板
                }))
              }
            }
PLAIN ENGLISH

导入扫描工具。

定义一个 paths() 函数，VitePress 会在构建期调用它来知道"要生成哪些动态路由"。

扫描 content/posts/ 拿到全部文章的元数据列表。

把每篇文章的 slug 与完整内容转成 VitePress 期望的格式：params 用于 URL，content 注入到 Markdown 模板里。

✦
Why paths.ts?

在 VitePress 这种"静态优先"的框架里，所有 URL 必须在构建期确定。paths.ts 就是"我有多少篇文章 / 多少个标签 / 多少个分类"的权威清单。

为什么它"默认安全"？

很多博客系统允许 v-html，让作者直接写 HTML 进去——这等于把 XSS 攻击的大门敞开。FilePress Blog 走的是 unified → remark → rehype → rehype-sanitize 的安全 AST 管线：

首屏性能：手动 chunk 拆分

KaTeX（数学公式）和 lucide-vue-next（图标库）都是"按需加载"的——只有当页面真的用到公式或图标时，对应 chunk 才会被请求。这是 .vitepress/config.mts 里 rollupOptions.output.manualChunks 的功劳：

.vitepress/config.mts 

                  vite: {
                    build: {
                      cssMinify: true,
                      minify: 'esbuild',
                      rollupOptions: {
                        output: {
                          manualChunks(id) {
                            if (id.includes('node_modules/katex')) return 'math'
                            if (id.includes('node_modules/lucide-vue-next')) return 'icons'
                          }
                        }
                      }
                    }
                  }
PLAIN ENGLISH

如果当前文件来自 katex 包，把它单独拆到名为 math 的 chunk。

如果来自 lucide-vue-next，拆到 icons chunk。

其余所有依赖留在主 chunk。

结果：没用公式 / 图标的页面，首屏 JS 包体积显著减小。

∑
math chunk

只在你写了 $$E=mc^2$$ 的页面才会被请求。

✦
icons chunk

Lucide 图标按需懒加载，主包不背图标树。

⚡
主 chunk

仅包含 VitePress 核心 + Vue 运行时 + 主题组件。

Module 04 · CLI 文章管理

post-cli：用一条命令管全部内容

post-cli 是一个零外部依赖的 Node.js 脚本集合（scripts/post-cli/），覆盖创建、更新、发布、列出、查看、部署全流程。学会它，就再也不用手动建文件了。

Quick reference

11 个子命令，一张表速查

所有命令都以 pnpm post <cmd> 触发，且全部有别名（pn、pu、pd …）以减少敲键：

pnpm post n <slug> 创建新文章（new）。必传 slug，-T 标题、-d 摘要、-t 标签、-c 分类、-C 封面图、--draft 草稿。
pnpm post u <slug> 更新 frontmatter。--append-tags 追加标签，--set-category 改分类，-y 跳过确认。
pnpm post p <slug> 把草稿发布上线（draft: true → false）。
pnpm post d [-y] 一键部署：预检 → 构建 → 推送 gh-pages → 清理临时文件。
pnpm post l 列出所有文章（标题、日期、分类、字数、阅读时长）。
pnpm post r <slug> 查看某篇的 frontmatter 与正文摘要。
pnpm post s [--open] 启动 vitepress dev，--open 自动打开浏览器。
pnpm post c 清理 .vitepress/cache、.vitepress/dist、node_modules/.vitepress。
pnpm post help [cmd] 查看所有命令或某个命令的详细帮助。

Practical takeaway

这就是为什么 FilePress Blog 推荐用 post-cli 而不是手动 touch 文件：CLI 写入的字段顺序固定、字段值合法、文件名字符符合 slug 规则——任何不合规都会在前置校验阶段被拦下。

内容约定：哪些字段是必填的？

FilePress Blog 推崇"约定优于配置"——大部分字段都可以省略，系统会自动回退到合理默认值：

T
title · 必填

缺失时自动取正文中第一个 # 一级标题。

D
date · 可空

默认 today，缺失时回退到文件 mtime。

S
description · 可空

缺失时自动取正文前 200 字符（去除 Markdown 标记）。

C
category · 可空

缺失时归入"未分类"。

#
tags · 可空

数组，可省略；v2.0 修复了中文 tag 的 URL slug 二次编码问题。

⏱
readingTime

200 字/分钟，CJK 按字符，英文按词数加权，在 utils/readingTime.ts 计算。

nginx.conf 片段 

server {
  listen 80;
  server_name blog.example.com;
  root /var/www/filepress-blog/.vitepress/dist;
  index index.html;

  location / {
    try_files $uri $uri/ =404;
  }

  # 启用 Gzip 压缩
  gzip on;
  gzip_types text/plain text/css application/json application/javascript;
}
PLAIN ENGLISH

try_files 先按路径找文件，找不到再 fallback 到 404（VitePress 自带 404.md 友好页）。

开启 Gzip 让 JS / CSS 资源体积更小。

这是 v2.0 修复前的 tagToSlug 早期实现，故意留了一个 bug。点你认为有问题的那一行：

Bug 定位 · tag → slug 转换

1 export function tagToSlug(name) {
2 const trimmed = name.trim()
3 const lowered = trimmed.toLowerCase()
4 return encodeURIComponent(lowered) // ← 关键行
5 }
✦
v2.0 修复

第 4 行的 encodeURIComponent 是问题根源。VitePress 在生成 URL 路径段时还会再编码一次，导致中文 tag 变成 ai-%E4%B8%8E...。v2.0 改为：return lowered.replace(/\s+/g, '-') —— 空格转连字符，中文直接透传。

8 个高频问题速查表

遇到问题先翻这张表：

Q1 pnpm install 慢 / 失败？ 切到国内镜像：pnpm config set registry https://registry.npmmirror.com。
Q2 如何自定义主题色？ 改 tailwind.config.js 里的 colors.moss，同时改 .vitepress/theme/styles/index.css 里的 --accent。
Q3 如何启用 Giscus 评论？ 5 步：开启 Discussions → 装 giscus App → 建分类 → 拿 ID → 写 .env。详见 docs/COMMENTS.md。
Q4 图片如何优化？ 放原始图到 assets/images/raw/，跑 pnpm images，自动生成 WebP + LQIP 模糊占位。
Q5 如何迁移到别的电脑？ 整个项目就是一份 git 仓库，git clone + pnpm install 三分钟内恢复全部内容。
Q6 RSS 怎么不更新？ pnpm rss 单独跑一次，或 pnpm dev 启动时会自动跑。
Q7 暗色模式怎么定制？ 改 .vitepress/theme/styles/index.css 里的 .dark { ... } 块。
Q8 构建产物在哪里？ .vitepress/dist/。可以整目录 rsync 到任意 Nginx / CDN / 对象存储。

调试心法：3 个"先看这里"

出问题别慌，按顺序查这三处：

01
终端报错信息

VitePress / Vite / TypeScript 的报错通常很具体，复制第一行错误码去搜，比看整页 stack trace 高效得多。

02
浏览器 DevTools Console

前端 JS 错误、404 资源、CORS 问题都会在这里冒出红字。F12 → Console 是 80% 问题的"第二现场"。

03
.vitepress/dist/ 输出

如果 dev 没问题但 build 失败，对比 dist 目录里的 HTML / 资源清单——是否被手动 chunk 拆错了、是否缺了某个依赖。

✦
万能兜底

如果实在搞不定，pnpm post c 清理一次缓存（约等于"重启 VitePress"），大多数怪异问题都会消失。实在不行就 rm -rf node_modules .vitepress/cache && pnpm install。
